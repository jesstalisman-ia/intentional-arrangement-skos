# v0.19.1 — a successor in another scheme, lifecycle checks, and an API error that says what was asked

Two tickets closed since the v0.19.0 post, both from @dpw67, plus a fix the code scanner asked for.

## Retire a concept in favour of one elsewhere

A concept superseded by one in another scheme, or in an external vocabulary, had nowhere to say so: Replaced by only took a concept of the same scheme (#140).

- **Lifecycle status now sits above External mappings**, and Replaced by takes a concept of this scheme from a picker, or any IRI with an optional label, written as `rdfs:label` on the target.
- **Export writes `dcterms:isReplacedBy` for both kinds**, and `dcterms:replaces` on a same-scheme successor. Import keeps an external successor as its IRI and mints no concept for it.
- **The mapping is chosen in the same step.** For an IRI successor you pick `skos:exactMatch`, the default, `skos:closeMatch`, or no mapping. The lifecycle statement and the mapping are both written, because they answer different questions: what replaces this concept, and how the two meanings relate.
- **Links to the retired concept are yours to redirect.** The panel counts the broader and related links other concepts still have to the retired one and offers one button: redirect them to the same-scheme successor, or remove them when the concept has gone to another scheme. A change note goes on every concept touched. Nothing changes without the press.
- **Notes and version.** Deprecation, reinstatement and replacement are recorded as dated `skos:historyNote` entries on the retired concept. The panel offers a one-click bump of `owl:versionInfo` and `dcterms:modified`, since a deprecation is a major change for anyone who indexed with the scheme.
- **A rename keeps the old name findable.** Changing a preferred label offers to keep the former label as an alternative label.

## Lifecycle checks

Doug's two observations on the validator became #144. Three rules now run in the in-app validator and as SHACL shapes in the API and the MCP server:

- A deprecated concept is not asked for a definition.
- A live `skos:broader` or `skos:related` link to a deprecated concept is a warning: the retired concept keeps its URI for old references, and the live structure should not point at it.
- A deprecated concept with neither a successor nor a mapping is a warning: readers of the old URI learn that it is retired and nothing more.

An IRI successor is no longer reported as dangling.

## An API error that says what was asked

A request for a format the engine does not offer is answered from the request itself: the source or target format that was asked for, and the lists of supported ones. Exception text is no longer sent to the client, which closes the code scanner's stack-trace-exposure alert.

## What changes in your exports

A same-scheme successor is now written with `dcterms:replaces`, and a deprecated concept with a history note of its deprecation. Both are additions. Nothing that was written before is written differently.
