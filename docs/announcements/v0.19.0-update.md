# v0.19.0 — validation you can gate on, a parse tool for grounding, eight engine fixes, labels for mappings, and deprecated concepts you can see

Seventeen tickets closed since the v0.18.13 post, every one filed by someone using the editor, the API or the MCP server for real work. Three people did the reporting; two of them ran the engine outside the browser and found what the browser never showed.

## Validation you can gate on

@dpw67 ran the REST API and the MCP server against a 267-concept vocabulary and found that the numbers did not add up (#123, #124).

- **`summary.violations` and `summary.warnings` now count SHACL results and structural findings together**, and `summary.info` counts the informational results. `shacl_conforms` keeps pySHACL's meaning, false whenever any result exists, info included, and `summary.no_violations` is the flag to gate on.
- **The profile tells the truth about soundness.** It reports SHACL counts by severity and `sound`, which is true only when nothing is at violation level, whether from SHACL or from the cycle and orphan checks. The REST API gained `POST /profile` so both interfaces report the same thing.
- **SHACL results are structured data** (#125): severity, shape as a CURIE, focus node and its label, path and message. `detail=summary` groups them by shape with each message once and drops the text report; it is the default for the MCP tool and a fraction of the size.
- **Four new shapes** (#127): an alternative label equal to another concept's preferred label in the same language, a one-way `skos:related`, whitespace inside a label, and whitespace around a note.

## The MCP server reads files and returns the vocabulary

A 370 KB Turtle file is about 100k tokens, too much for a model's tool call (#126). The three tools now take `file_path`, and `convert_skos` also `out_path`, switched on by the `IA_SKOS_FILES` environment variable that names the directories the server may touch; paths outside them are refused. A fourth tool, **`parse_skos_vocabulary`**, with `POST /parse` on the REST API, returns the vocabulary itself as plain data: schemes, counts and a page of concepts with labels, notes and relations, with a scheme filter, a label search, four levels of detail and paging. That is how a model grounds on a vocabulary too large to paste.

## RDF/JSON both ways, and an honest error

The API advertised RDF/JSON and could not write it (#122), because rdflib has no plugin for the format. The engine now reads and writes RDF/JSON itself, and a format it does not offer answers with a specific error and the list of supported ones, distinct from the message for malformed input.

## Eight engine fixes from a run against eighteen real vocabularies

@data-riot ran `core.js` under Node against 18 SKOS and JSKOS vocabularies, 403 concepts, and filed eight reports with the line and the fix for each (#128 to #135). All eight are in.

- A SPARQL variable used more than once in the WHERE clause keeps its bindings; the OPTIONAL case pairs each label with its own concept (#128).
- `LIMIT` and `OFFSET` work after `ORDER BY ASC(?x)` (#129), and `<` and `<=` work in `FILTER` (#130).
- One decoder for Turtle and SPARQL strings: `\u` and `\U` escapes, escaped quotes inside long strings, and a long string that ends in a quote (#131). Vocabularies in languages other than English imported with broken labels before this.
- A dotted local name such as `v1.2` survives a Turtle round trip, on the writing and the reading side (#132).
- RDF/XML declares a generated prefix for a predicate outside the built-in table instead of dropping the triple (#133).
- CSV, XLSX and Markdown write a concept's own URI (#134), and CSV import works wherever the engine is loaded as a library (#135).

## Labels for external mappings

@Morten-Munck asked for a display name on a mapped IRI, so the graph and the exports show "Car (Wikidata)" instead of a long URL (#137). Each mapping row takes an optional label, written as `rdfs:label` on the target IRI, read back on import, and used by the graph, the concept view and the Markdown export. One label per IRI, shared by every concept mapped to it.

## Deprecated concepts you can see

@dpw67 deprecated a concept and found it listed beside its successor with no mark (#139). A deprecated concept is now struck through with a **deprecated** badge in the tree and the browse views, the tree has a **Deprecated** toggle that hides retired concepts with no narrower concepts left, and when a deprecated concept has narrower concepts and a successor, the Lifecycle panel offers to move the children to the successor in one press, with a change note on each. The panel and the Duplicate action now say that a change of name alone is an in-place edit of the label or the local name; deprecation is for a change of meaning.

## Declined, with the reason

Opening the concept record to further Dublin Core terms, a few or all (#138), extends beyond the scope of a SKOS editor: the tool describes concepts with SKOS and keeps a curated set of Dublin Core Terms on the scheme, and every term added to concepts would need its own validation and export rules. Concepts imported with other DCMI triples keep them and write them back out.

## Tests now run on every push

`tools/test_core.js` runs the engine's SPARQL, Turtle and export paths under Node, with the eight reports above as regression cases; `tools/test_engine.py` covers the shared Python engine, the REST API and the MCP tools, Doug's repros included; `tools/smoke.py` still loads the page in headless Chrome. All three run in CI on every push.
